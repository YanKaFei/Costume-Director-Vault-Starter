## 2. 验证项 1：跨时代完整 outfit 硬约束与 Creative Override

### 2.1 严格 11th c Scotland 样本（PASS）

输入 `inputs/cross_era_macbeth.json`（historical / 11th c Scotland / storm / battle）：

```text
python3 scripts/outfit.py --input 11-验收/R1.1/CREATIVE/inputs/cross_era_macbeth.json --json
exit 3
status=blocked, looks=[], hard_constraints_passed=false, constraint_violations=5
```

violations 包含：no reliable period/region context、historical period/region unverified、cross-region borrowing 等；没有把错配 look 作为普通输出返回。**符合“完整 outfit 之后硬约束生效”。**

### 2.2 Creative Override（PASS）

同一输入 + 合法 override：

```text
exit 0
status=override
historical_accuracy=false
creative_override={"intent":"stylized stage Macbeth",
 "conflicts":["no exact 11th-c Scotland garments","cross-era analogue wardrobe"],
 "historical_accuracy":false}
looks=1, constraint_violations=5（保留冲突记录）
```

非法 override（`historical_accuracy: true`）：

```text
exit 3
status=blocked
looks=[]
historical_accuracy=false
```

**结论**：override 不能伪装历史准确；意图/冲突/`historical_accuracy=false` 都被记录。PASS。

### 2.3 普通输出不得含未声明错配（FAIL）

使用 P4-5 的 `macbeth_rise.json`（`period=medieval`、`region=europe`、`fidelity_mode=inspired`）——这正是 R1 审计 AUD-002 的 kirtle+trench+1930s 手袋样本：

```text

status=ok
looks=3
hard_constraints_passed=true

B = GAR-0009, GAR-0045, GAR-0081, GAR-0080, GAR-0048
C = GAR-0079, GAR-0045, GAR-0022, GAR-0080, GAR-0048
```

warnings 只有：

- no reliable period/region context card（medieval/europe）；
- period evidence approximate/none for **GAR-0022, GAR-0045**；
- wetness/damage/dirt unknown；
- items without source_ids: **GAR-0079**。

**问题**：1980s/1930s 手袋 `GAR-0048` 与 11th-c 场景的错配没有被逐项声明；`GAR-0079` 只被提示“无 source_ids”，没有被标为与 Macbeth 角色/年代不符。`GAR-0045`（trench）与 `GAR-0022`（威灵顿靴）只以“era-level hypotheses”泛化提示。`docs/OUTFIT-QUALITY.md` §5 也承认：*“a mixed look may pass with one anchor while retaining analogue pieces”*。

**判定：FAIL**（严格案例 PASS，但普通 inspired 输出仍含未声明错配；item-level era guard 未实现/未生效）。

## 3. 验证项 2：A/B/C 有意义差异

### 3.1 同视觉语言的单件替换（PASS）

用 `macbeth_rise-NEW` 的 A 复制出 B，只替换 A/B 唯一差异 `GAR-0079→GAR-0009`，并保持 A 的 palette/materials/silhouette：

```json
"synthetic same-vis one-item swap: pass=false, one_item_swap_gaming=true,
 all_pairs_meaningful=false, a_b={item_diff:2, slot_diff:1, silhouette_diff:false}"
```

这正是 `tests/test_r1_1_cd.py::test_one_item_swap_is_not_meaningful` 的断言；`abc_eval.evaluate` 对“单件且视觉语言不变”的交换判 gaming。**PASS。**

### 3.2 真实 A/B 单件替换被判 meaningful（FAIL，严格口径）

`abc_eval --input 11-验收/P4-MACBETH/inputs/macbeth_rise.json --json`：

```text
pass=true
all_pairs_meaningful=true
one_item_swap_gaming=false
a_b: item_diff=2, slot_diff=1, silhouette_diff=true (A vs H), meaningful=true
```

而 A/B 的实际单品集合只差 **一件**（`GAR-0079` vs `GAR-0009`）。原因是 evaluator 的规则：

```text
meaningful = item_diff >= 2 and (slot_diff >= 2 or silhouette_diff or material_diff >= 2 or palette_diff >= 2)
one_item_swap = item_diff == 2 and slot_diff < 2 and not silhouette_diff and material_diff < 2 and palette_diff < 2
```

当单件替换改变了 silhouette 推断时（A/H），它不再算 gaming，而被算 meaningful。若按任务字面“**单件替换不得判为有意义**”，此案例应当 FAIL。

**判定：FAIL（严格口径）**。建议：把“单件替换”与“有意义结构差异”分开报告；`meaningful` 至少要求 `slot_diff >= 2`（或人工定义的结构轴），而不是让 silhouette 单独豁免。

### 3.3 独立抽 5 组（非固定案例；WARN）

用 `outfit.py --brief` 新造 5 组未参与 R1.1-C/D 固定案例的输入，保存后分别 `abc_eval --outfit`：

## 8. Look Bible 可行性结论与建议

**可行，且 R1.1 已把最小闭环做出来**：

- 数据模型（项目级，不污染公共卡）：`character_id`、`look_id`、`version`、`status`（Draft/Proposed/Approved）、`approved_anchors`（hard/soft + approved_by/at）、`slots`、`scene_changes`、`sources`/`rationale`、`change_log`、`approvals`（signature_sha256、role、reviewer）、`proposed_at`/`approved_at`/`approved_by`；
- CLI 工作流：init / add / propose / approve / patch / diff / validate；
- 已证明：hard anchor 不可无意覆盖、soft patch 只产生 1 个 item diff、版本递增、Agent 自批被拒绝、validate PASS；
- 剩余要做的（不在本任务实现）：
  1. composer 直接消费 Approved Look Bible（hard anchors + version 锁定），而不是只接受 `approved_anchors` ID 列表；
  2. approval change_log 区分 reviewer 与 agent；
  3. 签名真实性（当前只查 role/agent 标记与 reviewer 名，未验证签名所有权）；
  4. 增加 revoke/supersede 状态与迁移 P3.5 18 套（含 2 个槽位缺口修复）；
  5. 与 P3.6 导演评分表联动时仍保持“签核 ≠ 分数、AI 不代填”。

**建议优先级**：先修 VR-01（普通输出错配）、VR-02（严格单件判定）、VR-03（回归），再做 composer×Look Bible 集成（VR-07）；否则 Look Bible 只是“审批记录”，不能约束生成。
